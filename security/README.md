# Chromium namespace sandbox policy

`chromium-seccomp.json` is a host-side Docker seccomp policy for the tested
linux/amd64, Docker 29.4.1, non-root UID 1000 Fleet contract. It is not a universal
replacement for every Docker release, architecture, or capability configuration.
The baseline is the effective OCI `linux.seccomp` generated by Docker for a
credential-free container with the default capability set, no capabilities added,
and `no-new-privileges`. It derives from Moby's Apache-2.0 default policy; see
https://github.com/moby/moby/blob/master/LICENSE . Provenance is recorded alongside
it. This is a runtime capture, not a claim that it matches a downloaded upstream
JSON file byte-for-byte.

The only changes are four appended exact argument-equality allowances:

| syscall | argument 0 | meaning |
| --- | --- | --- |
| clone | 0x10000011 | NEWUSER + SIGCHLD |
| unshare | 0x10000000 | NEWUSER |
| clone | 0x70000011 | NEWUSER + NEWPID + NEWNET + SIGCHLD |
| clone | 0x20000011 | NEWPID + SIGCHLD |

Each was observed denied during successive sandboxed Chromium startup traces.
All baseline rules, architectures, default action and the `clone3` ENOSYS behavior
are retained. The regression reconstructs and hashes the exact captured baseline
and checks the four additional rules. `mount`, `setns`, `bpf` and `keyctl` remain
outside its allow rules. Docker-default AppArmor, non-root identity and
no-new-privileges stay enabled. No SYS_ADMIN, unconfined policy, setuid helper,
host sysctl change, or disabled Chromium sandbox flags are needed.

## Security tradeoff

The necessary change permits these namespace operations to **every process in
the container**, not just Chromium. Seccomp cannot identify the calling program.
This exposes user-namespace kernel paths previously blocked by Docker's default;
it is a real security-policy change, not a claim of unchanged attack surface.
AppArmor and the remaining seccomp restrictions still apply. A static effective
policy also does not automatically inherit future Docker default hardening.
Re-review the baseline and repeat acceptance when changing Docker, architecture,
capabilities, kernel/AppArmor behavior, or the Chromium image.

## Activation contract

The deployment owner must first stage reviewed policy bytes at a root-owned,
non-writable host path and verify their digest. Add the policy to the existing
agent security options, **retaining** `no-new-privileges:true`. For a Compose file
beside the staged `security` directory:

```yaml
security_opt:
  - no-new-privileges:true
  - seccomp=./security/chromium-seccomp.json
```

The image must contain Agent support for `browser.sandbox_required: true`, and
the managed profile must set that leaf. Policy alone is insufficient: older
launchers automatically disable the sandbox inside Docker. Do not activate a
managed leaf before its image supports it. Do not change browser profile paths,
copy credentials, delete Singleton locks, or expose DevTools ports. This generic
asset does not start, recreate, or mutate any live service.

## Functional acceptance

Use `scripts/verify-chromium-sandbox.py` with the image's Python interpreter in a
**credential-free disposable container**, with an outer timeout, no network,
read-only root, writable temporary filesystem, UID 1000, no-new-privileges,
default capabilities, docker-default AppArmor and this exact policy. Mount only
the reviewed verifier read-only. Do not mount live state or run it in a gateway.
Run both its default headless mode and `--headed` for the Bot Desktop runtime.

The verifier launches through the installed canonical Agent launcher with a
new temporary managed profile. It requires namespace/PID/network sandbox and
seccomp-BPF/TSYNC diagnostics, real JavaScript rendering, and renderer UID 1000,
NNP=1, Seccomp=2, at least two seccomp filters, nested PID namespaces, and zero
effective capabilities. It also requires docker-default AppArmor. It prints
JSON and exits nonzero on failure. It does not attest arbitrary remote CDP
servers, host-native browsers, or the final image when candidate source was
mounted for a development probe.

Keep the exact image digest, source commits, policy SHA256 and result JSON with
the release. An `about:blank` dump, binary inventory, green unit tests, or a
source-mounted prototype alone is not deployment acceptance.

## Rollback

Before activation retain the exact previous image, per-target Compose security
options, and managed-leaf preimage. If the canary fails, stop the rollout and
restore that target through the existing reviewed recovery path; preserve all
browser state. Restoring the old policy restores the known sandbox startup
failure, so browser availability must remain explicitly failed/disabled rather
than silently launching without a sandbox. Do not fix a rollback by adding
`--no-sandbox`, privileges, or globally disabling host restrictions. Policy files
can remain installed but unused. The supervisor owns live changes and recovery.
